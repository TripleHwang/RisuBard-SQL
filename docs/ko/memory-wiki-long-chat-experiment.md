# 장기 채팅 단일 사례 실험: 전체 히스토리 없이 초반 사건을 기억할 수 있을까?

2026년 8월 22일, RisuBard의 BardWiki 메모리가 긴 역할극에서 먼 과거의 사건을 복원할 수 있는지 실제 채팅 한 세션으로 확인하고, 전체 transcript 방식의 입력 토큰을 반사실로 계산했습니다.

## 결과 요약

- 21번째 답변을 요청하면서 세션 초반 사건의 원인과 대안을 분석하도록 지시했습니다.
- 요청 로그의 `선택된 채팅 메시지`는 4개였고, 현재 사용자 요청과 관련 Wiki 문서 1개가 함께 전달됐습니다.
- 모델은 초반의 우유팩 사건, 사과를 거부한 태도, 리즐렛에게 한 폭언과 이후의 신발 훼손을 찾아 인과관계로 연결했습니다.
- 마지막 답변의 **측정값**은 입력 17,247토큰, 출력 1,969토큰, 요청 완료 16.8초였습니다.
- 같은 요청에 전체 transcript를 넣었을 때의 **추정 입력**은 약 67,950토큰으로, 실제보다 약 3.9배 큽니다.
- 0-based 메시지 index 41까지 전체 transcript와 기억 엔진을 함께 사용했다면 **추정 누적 입력**은 약 1,257,690토큰입니다. 실제 로그의 873,836토큰보다 383,854토큰, 약 43.9% 많습니다.

이번 결과는 한 세션에서 전체 기록 없이도 관련 Wiki를 이용해 초반 사건의 핵심 인과를 분석할 수 있음을 보여줍니다. 전체 transcript와의 속도·품질 우열은 비교 실행하지 않았으므로 별도의 반복 A/B 실험이 필요합니다.

## 기존 장기 채팅이 어려웠던 이유

일반적인 채팅은 이전 대화를 매 턴 프롬프트에 다시 넣습니다. 한 턴이 추가될 때마다 다음 요청이 조금씩 커지고, 세션 전체 누적 입력은 삼각형처럼 쌓여 대략 턴 수의 제곱에 비례해 증가합니다.

```text
1턴: 현재 대화
2턴: 1턴 + 현재 대화
3턴: 1턴 + 2턴 + 현재 대화
...
```

비용을 감수해 전체 기록을 넣더라도 모델이 긴 입력 중간의 작은 사건을 항상 정확히 찾아낸다고 보장할 수는 없습니다. 이를 보완하려고 별도의 요약·서사·기억 엔진을 함께 구동하면 전체 transcript 비용 위에 분석과 기억 생성 비용이 다시 추가됩니다.

결과적으로 기존 구성에는 다음 문제가 함께 발생했습니다.

- **속도 부담:** 매 턴 모델이 처리할 입력이 커집니다. 실제 지연은 모델, provider, prompt cache와 서버 상태에 따라 달라집니다.
- **품질:** 중요한 과거 사건이 긴 기록 사이에 묻히고, 현재 장면과 무관한 내용이 모델의 주의를 차지합니다.
- **비용:** 전체 transcript 재전송과 별도 기억 엔진 비용을 동시에 지불합니다.
- **한계:** 충분한 예산이 있어도 모델의 context 한도와 긴 입력에서의 검색 정확도 문제는 사라지지 않습니다.

## RisuBard의 접근

RisuBard는 채팅 원문을 삭제하지 않습니다. 원문은 근거로 보존하고, 확정된 사건과 지속 상태를 Markdown Wiki에 정리합니다. 새 답변을 만들 때는 다음 자료만 고정된 범위에서 선택합니다.

- 현재 사용자 요청
- 제한된 최근 원문
- 현재 질문과 관련된 캐릭터·사건·장소 문서
- 캐릭터와 세계관의 정적 설정

마지막 OOC 요청에서는 다음 현재 채팅 설정을 사용했습니다.

| 설정 | 값 |
| --- | ---: |
| Wiki 조회 목표 | 2,000토큰 |
| Wiki 조회 절대 상한 | 6,000토큰 |
| AI 분석 상한 | 12,000토큰 |
| 추가 검색 | 1회 |
| 자동 정본 대상 | 4개 |
| 분석 최근 원문 | 4개 |
| 답변 최근 메시지 | 4개 |
| 과거 사용자 메시지 | 제외 |
| 정본 문체 | 간결 |

## 실험 구성

테스트 세션은 0부터 시작하는 메시지 배열 index 0~41의 42개 메시지, 즉 사용자 메시지 21개와 활성 assistant 답변 21개로 구성되었습니다. 답변 재생성 2회를 포함하면 실제 메인 모델 요청은 23회였습니다. 재생성 요청은 해당 사용자 메시지까지의 동일한 활성 transcript 크기를 한 번 더 계산했습니다.

세션 초반에는 한 인물의 장난이 사고로 이어지고, 사과와 관계 회복에 실패하면서 인물 관계가 바뀌는 사건을 진행했습니다. 이후 장면을 충분히 진행한 다음 사용자 메시지 index 40에서 역할극을 중단하고 초반의 결정적 실패와 가능한 대안을 물었습니다. assistant 메시지 index 41이 분석 답변입니다.

실험 모델은 `gemini-3.7-flash (Vertex AI)` plugin provider였습니다. sampling 설정은 증거 보고서에 기록되지 않았습니다. 입력 토큰과 요청 완료 시간은 RisuBard 요청 로그의 값을 사용했으며 첫 토큰 시간은 provider에서 제공되지 않았습니다.

초반 사건의 Wiki는 세션의 확정 턴마다 자동으로 생성·갱신됐습니다. 마지막 OOC 요청에 선택된 `니시카타` 문서는 OOC 요청보다 약 17분 전에 마지막으로 갱신됐으며, 아직 생성되지 않은 OOC 답변의 정보를 포함하지 않았습니다.

마지막 요청에 실제로 들어간 서사 자료는 다음과 같습니다.

| 자료 | 입력 토큰 |
| --- | ---: |
| 최근 채팅 기록 | 10,447 |
| 관련 Wiki `니시카타` 문서 | 1,975 |
| 시스템·캐릭터·로어 등 기타 입력 | 4,825 |
| 전체 입력 | 17,247 |

초반 원문은 선택된 최근 채팅 기록에 포함되지 않았습니다. 모델은 Wiki에 정리된 인물의 작중 행적을 통해 초반 사건을 복원했습니다.

## 답변 품질

index 41의 답변은 다음 분기점을 찾아냈습니다.

1. 사고 자체보다 사고 이후 책임을 회피하고 사과를 무효화한 태도가 관계 단절의 핵심이었다.
2. 조언을 열등감과 폭언으로 되받은 행동이 갈등을 심화했다.
3. 질투를 노력이나 정당한 경쟁이 아니라 신발 훼손으로 표출하면서 주인공의 위치를 잃었다.
4. 사고 직후 솔직하게 사과하고 상대를 돌봤다면 기존 관계를 유지할 수 있었다.

전체 줄거리를 다시 전달하지 않았는데도 사건 목록을 나열하는 데 그치지 않고, 어떤 행동이 원인이고 어느 지점에서 다른 선택이 가능했는지 분석했습니다. 이 평가는 다음 간단한 기준으로 수행했습니다.

| 평가 항목 | 결과 |
| --- | --- |
| 질문에 필요한 핵심 사건 회수 | 4개 모두 회수 |
| 핵심 인과와 대안 제시 | 충족 |
| 세부 사실 정확성 | 작은 압축 오류 2개 |
| 전체 transcript 답변과의 품질 비교 | 실행하지 않음 |

완벽한 원문 재현은 아니었습니다. 답변은 필통을 상대에게 던진 것처럼 압축해 표현했지만 원문에서는 책상 위에 내던졌고, 신발 훼손은 최초의 감정 단절 원인이라기보다 이미 시작된 관계 악화를 심화한 사건이었습니다. 핵심 인과는 유지됐지만 세부 표현에는 이런 작은 오차가 있었습니다.

## 입력 토큰 비교

모든 수치는 같은 세션의 요청 로그와 `cl100k_base` tokenizer로 계산했습니다. 실제 provider의 내부 tokenizer와 완전히 같다고 보장하지 않으며, cache token은 공급자 로그에서 확인할 수 없어 비캐시 원시 입력 토큰을 사용합니다. 아래의 ‘비용’은 청구 금액이 아니라 모델별 단가를 적용하기 전의 입력 토큰량입니다.

### 마지막 요청 한 번

index 41 직전까지의 전체 transcript는 현재 사용자 요청을 포함해 63,125토큰이었습니다.

| 방식 | 마지막 요청 입력 | 실제 대비 |
| --- | ---: | ---: |
| 실제 RisuBard | 17,247 | 1.00배 |
| 전체 transcript, Wiki 미사용 | 약 67,950 | 3.94배 |
| 전체 transcript + Wiki 문서 | 약 69,925 | 4.05배 |

실제 요청은 16.8초에 완료됐습니다. 전체 transcript 방식은 실제로 재실행하지 않았으므로 가상의 생성 시간이나 속도 개선률을 제시하지 않습니다. 반사실에서는 입력이 약 네 배이므로 처리해야 할 prompt와 context 한도 부담이 커지지만, 실제 지연 차이는 별도의 실행 측정 대상입니다.

### index 41까지 누적 입력

23번의 메인 요청마다 당시의 전체 transcript를 다시 넣었다면 transcript 부분만 누적 675,399토큰입니다. 실제 RisuBard가 메인 요청에 넣은 제한 채팅 기록은 누적 291,545토큰이었습니다.

| 구성 | 누적 입력 토큰 | 실제 대비 | 의미 |
| --- | ---: | ---: | --- |
| 실제 RisuBard | 873,836 | 1.00배 | 제한 최근 원문 + Wiki 조회 + Wiki 분석·갱신 |
| 전체 transcript만 사용 | 약 894,532 | 1.02배 | 별도 기억 엔진 없음 |
| 전체 transcript + 기억 엔진 | 약 1,257,690 | 1.44배 | 기존 장기 채팅을 보완하려던 현실적인 구성 |

`전체 transcript만 사용`과 실제 RisuBard의 총량 차이가 작아 보이는 이유는 RisuBard가 답변 밖에서 Wiki 분석과 정본 갱신을 수행하기 때문입니다. 실제 로그에서 이 기억 작업은 입력 322,812토큰을 사용했습니다. 또한 실제 메인 요청에 주입된 Wiki 문서는 누적 40,346토큰이었습니다. transcript만 사용하는 반사실에서는 두 항목을 모두 제거했습니다.

```text
551,024 - 291,545 - 40,346 + 675,399 = 894,532
```

- `551,024`: 실제 메인 요청 23개의 전체 입력
- `291,545`: 실제로 선택된 제한 채팅 기록
- `40,346`: 실제로 선택된 Wiki 문서
- `675,399`: 같은 23개 요청에 전체 transcript를 넣었을 때의 누적 기록

실제 RisuBard는 기억 작업 결과를 다음 답변에서 다시 활용할 수 있고, 세션이 길어져도 답변 프롬프트가 전체 기록 크기를 따라 계속 증가하지 않습니다.

기존처럼 전체 transcript와 기억 엔진을 함께 사용한다고 가정하면 계산은 다음과 같습니다.

```text
873,836 - 291,545 + 675,399 = 1,257,690
```

- `873,836`: 실제 전체 입력
- `291,545`: 실제로 선택된 제한 채팅 기록
- `675,399`: 같은 23개 요청에 전체 transcript를 넣었을 때의 누적 기록

이 비교는 기존 기억 플러그인의 실제 비용을 측정한 값이 아닙니다. ‘전체 transcript + 기억 엔진’ 행은 비교 가능한 계산을 위해 동일한 RisuBard 기억 작업과 Wiki 주입을 유지하고, 제한 채팅 기록만 전체 transcript로 교체한 반사실입니다.

## 세션이 길어질수록 생기는 차이

평균 턴 길이가 비슷하다는 조건에서 전체 transcript 방식은 한 턴이 추가될 때마다 다음 모든 요청에 그 턴이 반복해서 포함됩니다. 턴별 입력은 선형으로 커지고 세션 누적 입력은 대략 `O(n²)`로 증가합니다.

RisuBard는 최근 원문 수, Wiki 조회 토큰과 분석 입력 토큰에 고정 상한을 둡니다. 이 상한이 유지되고 한 턴의 정본 작업도 설정 한도를 넘지 않는 조건에서는 저장된 원문과 Wiki가 늘어나더라도 메모리 관련 입력 비용은 정해진 범위 안에서 움직이고 세션 누적 비용은 대략 `O(n)`에 가깝게 증가합니다. 현재 사용자 입력, 정적 설정과 모델 출력은 이 상한에 포함되지 않습니다.

이번 21답변 세션은 두 방식의 총비용 차이가 본격적으로 벌어지기 전의 비교적 짧은 사례입니다. 그럼에도 마지막 단일 요청의 반사실 계산에서는 약 네 배의 입력 차이가 나타났습니다. 수십~수백 턴으로 이어질수록 전체 transcript의 반복 비용은 커지지만 RisuBard의 메모리 관련 입력 예산은 같은 상한을 유지합니다.

## 무엇을 확인했는가

이번 실험에서 확인한 것은 다음과 같습니다.

- 요청 로그의 선택 채팅 메시지가 4개인 상태에서도 관련 Wiki가 준비돼 있으면 먼 과거의 사건을 분석할 수 있었습니다.
- 전체 transcript를 보내지 않아도 사건의 원인, 결과와 대안까지 복원할 수 있었습니다.
- 마지막 답변은 장기 서사 질문에 답했으며, 전체 transcript 반사실보다 입력이 약 4분의 1인 것으로 계산됐습니다.
- 실제 누적 입력은 전체 transcript와 기억 엔진을 병행하는 반사실 구성보다 약 30.5% 적은 것으로 계산됐습니다. 반대로 반사실 구성은 실제보다 약 43.9% 더 많은 입력입니다.
- 세부 사실의 작은 압축 오차는 남아 있으므로, Wiki 정본의 품질과 사건별 근거 연결은 계속 중요합니다.

이 결과는 모든 모델과 모든 이야기에서 동일한 품질이나 속도 개선을 보장하지 않습니다. 이 세션에서는 전체 기록 없이도 핵심 인과 분석이 가능했습니다. 다른 이야기·모델·설정에서의 일반화와 전체 transcript 대비 품질·속도 우열은 반복 A/B 실험으로 확인해야 합니다.
