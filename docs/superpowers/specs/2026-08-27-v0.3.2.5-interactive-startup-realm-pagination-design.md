# RisuVault v0.3.2.5 Interactive Startup, Realm Cache, and Pagination Design

## Purpose

v0.3.2.5 closes the gap between a quickly painted shell and a genuinely usable application. The Node SQL startup must expose the home and RisuRealm surfaces as soon as the shallow bootstrap is ready, while data-dependent mutation features remain locally guarded until deferred hydration completes. The release also adds a bounded persistent stale-while-revalidate cache for the default RisuRealm feed and replaces exposed message pages with continuous, bounded history scrolling.

The design keeps the existing relational SQLite, lazy character/chat/message hydration, and saver-mode memory reclamation. It does not copy the entire Haejeok implementation or trade data safety for an unconditional early unlock.

## Success criteria

- On a normal metadata-first Node boot, the RisuRealm home, character summaries, and safe navigation become interactive immediately after the shallow SQL bootstrap and first paint.
- The application does not wait for the idle-callback timeout, deferred settings, plugin bodies, presets, global normalization, baseline cloning, or plugin/model/module initialization before enabling the safe shell.
- Character editing, chat generation, imports, settings, presets, plugins, organizers, and other mutation-heavy features remain locally unavailable until their required data is ready. The whole application is never made inert solely because deferred hydration is running or has failed.
- Selecting a character summary continues through the existing `changeChar` hydration path. Selection changes only after the matching full character record is available, and rapid selections cannot let an older request replace the latest intent.
- Deferred completion retains the existing safe order: merge deferred domains, run full normalization once, establish the SQL patch baseline, start metadata persistence, then enable the remaining feature domains and deferred modules.
- RisuRealm immediately displays a valid previously cached default feed when present, always starts a background refresh on a new app session, and replaces the cache only after a successful validated response.
- RisuRealm failures do not erase a cached feed or masquerade as a successful empty result. Arbitrary searches, NSFW results, alternate sorts, pages, images, and server-provided HTML are not persistently cached.
- Older SQL-backed messages remain reachable by scrolling upward, including the short-message case where the initial 40 rows do not create a scrollbar. The interface exposes no Previous/Next page boundary, and Latest aligns the newest message to the viewport bottom.
- Scrolling through sequential persisted message IDs never omits, duplicates, reorders, or overwrites a row. The active DOM remains bounded to 60 messages in normal mode and 40 in saver mode even when the loaded history array grows on demand.
- Existing saver-mode behavior remains connected: dirty SQL flush, hydrated-chat eviction, 60-to-40 message-window reduction, parser/inlay cache clearing, and stable return to normal mode.

## Approaches considered

### Chosen: safe shell plus feature-local readiness

Remove the global inert gate after the shallow bootstrap, but retain an explicit deferred-readiness state. Home, Realm, character-summary navigation, and nonmutating shell controls remain usable. Features that depend on deferred domains render a local loading/disabled state and do not mutate partial data.

This provides the earliest real interaction without exposing every component to an incomplete database. It also allows a deferred-hydration failure to leave useful recovery and browsing surfaces available.

### Rejected: keep the global gate and make hydration faster

Starting deferred work sooner and optimizing cloning would reduce the delay but would preserve the misleading state where the app looks ready and ignores input. It also makes first-interactive latency scale with plugin, prompt, persona, and preset data.

### Rejected: unlock every feature against the shallow graph

This is visually fastest but repeats the v0.3.2.3 persona crash pattern across settings, organizers, plugins, character editors, and generation. Running global normalization early is also unsafe because defaults may overwrite missing deferred domains.

## Startup readiness architecture

### Safe-shell boundary

The safe-shell boundary occurs after `openExistingStandaloneSql()` returns a metadata-first result, `setDatabaseLite()` installs the shallow graph, essential language/theme/layout state is applied, and the browser has painted. The shallow graph remains limited to essential settings, character summaries, chat summaries/counts, selection identifiers, and the SQL revision.

`loadedStore` continues to mean that the visible application shell may render. Deferred readiness is tracked separately and no longer maps to an `inert` attribute on the complete application subtree.

The first-interactive metric is recorded when safe-shell input is enabled. A separate deferred-hydration duration records the later merge/normalization/baseline/persistence completion so performance reports cannot hide the difference.

### Scheduling

Deferred SQL hydration starts immediately after the first paint rather than waiting for `requestIdleCallback` with a two-second timeout. Nonessential tasks such as update checks, cleanup, and job recovery may retain idle scheduling.

This preserves the first paint while avoiding an artificial delay before settings and editors become available.

### Feature-local gates

Before deferred readiness:

- Allowed: RisuRealm browsing/search UI, cached Realm results, character-summary list/filter/sort, navigation back to Home, and character selection through `changeChar`.
- Allowed after local record hydration: read-only character/chat display and bounded message hydration.
- Blocked locally: message generation and mutation, character/chat configuration, drag/drop imports, exports, settings, presets, plugin actions, organizers, scripts, modules, lorebook/persona editors, and playground mutation surfaces.

Blocked controls show one shared compact loading state rather than silently ignoring input. The gate is enforced at the feature boundary in addition to hiding unsafe panels, so keyboard shortcuts and drag/drop cannot bypass it.

The global database must never pass through `setDatabase()` while still shallow. Full normalization happens only after deferred settings, plugin custom storage, and bot presets have merged. SQL dirty persistence remains off until the patch baseline has been established from that complete normalized graph.

### Failure behavior

A deferred failure records a failed readiness state, keeps the safe shell operational, and offers retry/reload/recovery guidance outside any gated feature subtree. Mutation features remain disabled. A retry reuses the same serialized hydration operation; concurrent retries cannot start duplicate merges.

## RisuRealm stale-while-revalidate cache

### Persistent scope

A dedicated cache module uses the existing persistent key-value abstraction with one versioned key:

`cache/realm/default-browse.v1.json`

Only the exact default request is eligible: empty text/tag search, page 0, SFW, and `recommended` sort. Search results, alternate sorts, pagination, random results, NSFW content, images, and `additionalHTML` remain transient.

The schema is:

```ts
type RealmDefaultBrowseCacheV1 = {
    version: 1
    fetchedAt: number
    cards: hubType[]
}
```

The cache accepts at most 100 validated cards and at most 1 MiB serialized metadata. Strings, tag counts/lengths, booleans, and numeric fields are bounded and normalized before display or storage. Entries older than 24 hours are not used as the initial display, but a failed refresh never overwrites or deletes an otherwise valid stored value. No image bytes are written.

### Load and refresh flow

On Realm mount, the component reads and validates the default cache. A valid entry is rendered immediately with a nonblocking refreshing state. One network request then fetches the latest default feed. A successful validated response replaces the visible cards and atomically overwrites the cache, including a legitimate empty feed. Transport, HTTP, parse, schema, and abort failures retain the cached display.

Nondefault searches keep the current page visible only until their own loading state is established; cached default cards are never labeled as search results. An incrementing request generation and `AbortController` cancel obsolete work. Only the latest matching request may update the UI, response-local HTML, or persistent cache.

`getRisuHub` stops mutating its input and stops converting all failures to `[]`. Its result distinguishes a successful empty card list from failure and returns response-local additional HTML. The HTML is never cached and is deterministically cleared when absent.

### Images and memory

Realm card images use native lazy loading and asynchronous decoding. The browser HTTP cache remains responsible for image responses; RisuVault does not persist image blobs.

The component holds only the current page of cards. Any transient parsed cache mirror is at most one entry and registered with the existing reclaimable-cache registry; the persistent metadata remains on disk and is unaffected by saver-mode memory clearing.

## Continuous message history

### Root causes

Node SQL intentionally hydrates only the newest 40 messages. The visible page count is currently calculated from those 40 local rows rather than the durable SQL total. When older rows exist but the local page count is one, the entire pagination control is hidden. If the 40 rows are short enough to fit without scroll extent, the reverse-scroll trigger also cannot fire. Older rows remain in SQLite but have no UI route and appear truncated.

Separately, `Chats` resets its internal window anchor to `pageEnd - 1`. When a visible page contains more than the normal/saver DOM cap, only the last 60/40 rows are mounted, so a page-top request can target the middle of the page. The explicit Latest path also aligns the newest message with `block: 'start'`, placing it at the physical top instead of the bottom.

### Continuous-scroll contract

Storage pages remain an internal transport detail. The user sees one continuous history:

- The Previous/Next/page-count navigation is removed.
- The mounted window spans the currently loaded message array rather than a user-visible page. Approaching the visual top first shifts the bounded DOM window toward older already-loaded rows. When that window reaches the local beginning and SQL reports `hasOlder`, the next reverse SQL chunk is fetched, validated, prepended, and anchored to the previously visible message identity.
- Approaching the visual bottom shifts the bounded DOM window back toward newer already-loaded rows. The normal/saver DOM cap remains 60/40 in both directions.
- After initial hydration, if the loaded rows do not create a scrollable viewport and SQL reports older history, older chunks load serially until the viewport is scrollable or history is exhausted. A failed fetch exposes a compact retry control at the visual top; it never clears the current rows.
- Latest is a viewport action, not a page action: anchor the bounded DOM window at the newest row and align that row to the viewport bottom.
- Initial open and live-stream auto-scroll remain latest-oriented unless the user has moved away from the tail.
- The alternate first greeting renders only when the oldest persisted message boundary is actually available, not merely because the local array begins at index zero.

The scroll implementation uses child component APIs that wait for the bounded window to commit before measuring or scrolling. It does not query a parent DOM that may still contain the previous window. SQL `total`, positions, cursor continuity, and stable message IDs remain the authority for completeness; local array length is never treated as the durable history total while `hasOlder` is true.

## Verification strategy

Testing remains scenario-focused.

1. A startup readiness scenario holds deferred hydration unresolved and proves Home/Realm and character-summary navigation are usable while mutation domains, persistence, plugins, and global normalization remain blocked. It then resolves hydration and verifies the merge → normalize → baseline → persistence → feature-ready order. A failure scenario proves the safe shell stays usable while mutation gates remain closed.
2. A character-entry scenario selects a shallow summary, verifies full-character replacement by stable `chaId`, bounded chat hydration, and latest-intent behavior for rapid selection.
3. A Realm cache scenario covers valid-cache immediate display, background refresh replacement, failed refresh preservation, successful empty results, bounded schema rejection, default-only persistence, and out-of-order request cancellation. One UI scenario verifies loading/refresh state and lazy image attributes.
4. A mounted continuous-history scenario seeds SQL with sequential IDs `m0…m80`, hydrates `m41…m80`, and uses a nonoverflowing viewport. It verifies automatic fill or the top retry path makes older history reachable, two reverse loads produce exactly `m0…m80` without duplicates, upward/downward movement keeps the DOM at 60/40, the visible anchor does not jump after prepend, and Latest places `m80` at the bottom. Source-string assertions are not accepted as the behavioral proof.
5. Existing saver-mode, chat hydration/LRU, SQL startup, plugin/settings, Realm experience, and message-window suites run as focused regression gates. Final verification runs the complete client/server tests, type checking, production build, release/compatibility gate, and performance contract.

## Implementation boundaries

Work proceeds sequentially in the shared isolated worktree to avoid overlapping edits:

- Startup implementer: readiness state, safe-shell/local mutation gates, immediate-after-paint hydration scheduling, metrics, and startup/selection behavior tests.
- Realm implementer: bounded persistent cache module, typed/cancellable Realm fetch result, SWR UI, lazy images, and cache/race tests.
- Continuous-history implementer: bidirectional bounded DOM window, automatic reverse SQL loading, committed-window scrolling APIs, removal of page controls, and mounted DOM/message-integrity regression.
- Reviewers: each implementation receives separate specification-compliance and code-quality review before the next task; a final integration review covers the combined diff.

All implementation and review agents use Terra medium as requested. Production changes follow red-green TDD with a small number of end-to-end behavioral tests rather than many microscopic assertions.

## Release boundaries

v0.3.2.5 does not replace SQLite, cache private Realm searches, persist Realm images or server HTML, enable Cloudflare uploads, redesign settings/editors, or remove existing memory saver behavior. The release is complete only after PR CI passes, the merge commit is tagged, four portable artifacts and the update manifest are verified by name/size/SHA-256, and the release is published as the latest stable version.
