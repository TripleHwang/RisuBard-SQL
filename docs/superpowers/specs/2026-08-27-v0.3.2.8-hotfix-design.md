# RisuBard v0.3.2.8 핫픽스 설계서

작성일: 2026-08-27

대상 기준: RisuBard v0.3.2.7 / Android 14 / Node 환경

상태: 조사 및 설계만 완료. 이 문서 커밋에는 제품 코드 변경이 없다.

## 1. 범위와 우선순위

| 우선순위 | 영역 | 상태 | 사용자 영향 |
|---|---|---|---|
| P0 | SQL 캐릭터 본문 복구 | 원인 확정 | 캐릭터 선택 불가 |
| P0 | Svelte SQL 런타임 메타데이터 | 원인 확정·재현 | 캐릭터/채팅 로딩 중 예외 |
| P1 | 캐릭터 전용 페르소나 이미지 | 코드 결함 확정 | 일부 이미지가 영구적으로 엑박 표시 |
| P1 | 플러그인 업데이트 | 실패 구조 확정, 대상별 직접 원인은 로그 필요 | `+` 버튼에서 일반 실패만 표시 |
| P2 | 설정 로딩 UI | 차이 및 안전한 통일 범위 확정 | 로딩 경험 불일치 |

릴리스 순서는 P0 데이터 접근 오류를 먼저 막고, 같은 핫픽스에 페르소나 자산 보존과 플러그인 진단/업데이트 경로를 포함한다. 설정 로딩 UI는 상태 로직을 건드리지 않는 표시 계층 변경으로만 포함한다.

## 2. SQL 캐릭터 복구 실패

### 증상

```text
Error: SQL character repair did not restore the character body
    at src/ts/storage/sql/sqlRuntimeHydration.ts
```

### 확정 원인

1. `server/node/sql-character-repair.cjs`는 현재 SQL 행이 collapsed 상태여도 단일 백업에서 유효한 후보를 못 찾으면 `not-needed`를 반환한다.
2. 클라이언트 `src/ts/storage/sql/sqlRuntimeHydration.ts`는 `not-needed`를 성공 또는 경합 복구로 해석해 다시 읽고, 본문이 그대로 collapsed면 위 오류를 던진다.
3. 서버 라우트는 `pre-sql-migration-v1.bin || database.bin`으로 백업 blob 하나만 선택한다. 첫 파일이 존재하지만 해당 캐릭터가 없거나 본문이 비어 있으면 두 번째 파일은 확인하지 않는다.
4. 현 테스트가 이 잘못된 `not-needed` 계약과 단일 소스 선택을 고정하고 있다.

### 필요한 패치

- 복구 입력을 우선순위가 있는 제한된 후보 목록으로 변경한다.
  1. `database/pre-sql-migration-v1.bin`
  2. `database/database.bin`
  3. 최신 `database/dbbackup-*` 일부(개수와 총 디코딩 용량 제한)
- 각 후보의 디코딩 실패, ID 불일치, 빈 본문은 다음 후보로 계속 진행한다.
- exact `chaId`와 의미 있는 본문을 모두 만족하는 첫 후보만 원자적으로 적용한다. 여러 백업을 필드별로 합치지 않는다.
- 현재 행이 이미 정상일 때만 `not-needed`를 반환한다.
- 현재 행이 collapsed이고 모든 후보가 소진되면 `unavailable`과 원인 코드(`no-candidate`, `decode-failed` 등)를 반환한다.
- 클라이언트는 상태별 사용자 메시지를 구분하고, 실패 시 기존 메타데이터 행을 손상시키지 않는다.

### 주의사항

- 의도적으로 빈 캐릭터와 collapsed 데이터의 구분은 현재 marker 계약을 유지해야 한다.
- 오래된 백업으로 새 빈 캐릭터를 되살리지 않도록 exact ID, 결정적 우선순위, 총 처리 예산이 필요하다.
- canonical character projection은 보조 후보가 될 수 있지만 이미 손상된 데이터일 수 있어 백업보다 먼저 신뢰하면 안 된다.

### 검증 항목

- 첫 백업에는 대상이 없고 두 번째 백업에는 대상이 있는 경우 복구
- 첫 백업 디코딩 실패 후 다음 백업 복구
- 모든 후보에 대상이 없으면 `unavailable`
- 정상 캐릭터만 `not-needed`
- genuinely blank 캐릭터를 임의로 복구하지 않음
- 복구 실패 후 SQL 행이 변경되지 않음

## 3. Svelte `state_descriptors_fixed`

### 증상

```text
Error: https://svelte.dev/e/state_descriptors_fixed
    at Object.defineProperty
    at src/ts/storage/sql/sqlRuntimeHydration.ts
```

### 확정 원인

- `DBState.db`는 Svelte `$state` 프록시다.
- `src/ts/storage/sql/sqlRuntimeHydration.ts`의 `setWindow()`가 reactive chat 객체에 `_sqlWindow`를 `enumerable: false`로 `Object.defineProperty()` 한다.
- Svelte 5 프록시는 고정 descriptor를 허용하지 않으므로 실제 프록시에서 동일 오류가 재현된다.
- `src/ts/storage/sql/sqlDirtyCommit.ts`의 `_sqlPosition`도 reactive message에 같은 방식으로 붙일 수 있어 후속 오류 경로다.
- 기존 단위 테스트는 plain object만 사용해 프록시 계약 위반을 잡지 못한다.

참고: [Svelte `state_descriptors_fixed` 공식 설명](https://svelte.dev/docs/svelte/runtime-errors#Client-errors-state_descriptors_fixed)

### 필요한 패치

- `_sqlWindow`와 `_sqlPosition`을 단순 enumerable 문자열 필드로 바꾸지 않는다. 백업, JSON, msgpack 또는 SQL extension data로 유출될 수 있다.
- Symbol 키 기반 런타임 메타데이터 helper를 추가하고 assignment로 저장한다.
- window/position의 get/set을 helper로 중앙화한다.
- 다음 직접 접근부를 accessor로 전환한다.
  - `src/ts/storage/sql/sqlRuntimeHydration.ts`
  - `src/ts/storage/sql/sqlDirtyCommit.ts`
  - `src/ts/storage/chatStorage.ts`
  - `src/ts/storage/sql/sqlDelta.ts`
  - `src/ts/characters.ts`
  - `src/ts/globalApi.svelte.ts`
  - `src/ts/plugins/plugins.svelte.ts`
  - `src/ts/process/index.svelte.ts`
  - 관련 Svelte 화면과 백업/패키지 코드

### 검증 항목

- 실제 `$state` 프록시로 최초 window 부착, 이전 메시지 prepend, 새 메시지 dirty commit 수행
- 예외가 없고 window/position 의미가 유지됨
- `Object.keys`, JSON, snapshot 및 영속 SQL payload에 런타임 메타데이터가 노출되지 않음
- plain object 경로와 프록시 경로를 모두 확인

## 4. 설정 로딩 UI 통일

### 현재 차이

- 캐릭터 로딩은 `src/lib/Others/LoadingOverlay.svelte`와 `loadingOverlayStore`를 사용한다.
- 설정 로딩은 `src/lib/Others/DeferredStartupGate.svelte`가 별도 backdrop, 색상, spinner, 영어 고정 문구를 렌더링한다.
- 설정 gate는 설정 외 preset, persona, bookmark, vault 등에도 재사용되며 `absolute/z-50` 범위가 기존 화면 계약이다.

### 필요한 패치

- 캐릭터와 설정의 로딩 **상태 store는 합치지 않는다**. 합치면 동시 작업에서 last-writer-wins 충돌이 생긴다.
- 공통 표시 shell을 추출하거나 `DeferredStartupGate`의 표현만 다음과 같이 맞춘다.
  - 동일한 backdrop 농도, 흰색 spinner/text, 간격과 typography
  - `role="status"`, spinner `aria-hidden="true"`
  - 로딩 문구 현지화
- 배치 의미는 유지한다.
  - 캐릭터: `fixed`, `z-[60]`, 선택적 취소 가능
  - 설정/deferred gate: `absolute`, `z-50`, 취소 버튼 없음
- hydration 실패/retry 분기는 기존대로 유지한다.

### 검증 항목

- 데스크톱·모바일 설정, Quick Settings, Vault의 local gate 범위 유지
- 캐릭터 선택 overlay의 취소/lifecycle 유지
- 설정 hydration과 캐릭터/채팅 전환이 겹쳐도 서로 overlay를 끄지 않음
- 로딩 및 오류 문구의 접근성/현지화 확인

## 5. 일부 페르소나 이미지 엑박

### 확정 원인

주원인은 WebP/PNG MIME 불일치가 아니라 캐릭터 전용 페르소나 자산이 garbage collection 생존 목록에서 빠진 것이다.

1. 아이콘은 `assets/<content-hash>.png` 키로 KV에 저장된다.
2. 글로벌 페르소나는 `db.personas`, 캐릭터 전용 페르소나는 `character.personas`에 있다.
3. `src/ts/bootstrap.ts`의 `cleanChunks()`는 `getUncleanables()`가 수집하지 않은 `assets/` 키를 삭제한다.
4. `src/ts/globalApi.svelte.ts`의 `getUncleanables()`는 글로벌 `db.personas[].icon`은 수집하지만 `db.characters[].personas[].icon`은 수집하지 않는다.
5. 캐릭터 전용 페르소나만 참조하는 고유 아이콘은 고아로 오판되어 삭제되고, DB의 icon 경로만 남아 Node asset route에서 404가 발생한다.
6. 서버 자산 통계용 `buildUncleanableSet`도 같은 누락이 있어 해당 파일을 고아 자산으로 잘못 표시한다.

“일부만” 깨지는 이유도 일치한다. 글로벌 페르소나 또는 캐릭터 본체와 같은 content hash를 공유한 파일은 살아남고, 캐릭터 전용 페르소나만 참조하는 고유 파일만 삭제된다.

Node와 비-Node 경로 모두 실제 매직 바이트로 PNG/JPEG/GIF/WebP MIME을 판별하므로 `.png` 키에 WebP 바이트가 저장된 경우는 현 버전에서 처리된다.

### 필요한 패치

- 클라이언트 `getUncleanables()`와 서버 `buildUncleanableSet()` 양쪽에 모든 `character.personas[].icon`을 추가한다.
- 중복 경로는 set으로 제거하고 빈 값/외부 URL/data URL은 자산 키로 오인하지 않는다.
- 자산 정리 전 참조 소유권을 공통 helper로 계산해 클라이언트와 서버 규칙이 다시 어긋나지 않게 한다.
- 이미지 렌더러에는 404/error fallback을 추가해 깨진 아이콘 대신 placeholder를 표시한다.
- 이미 삭제된 바이트는 DB 경로만으로 복구할 수 없다. 백업의 `assets/` 데이터가 있으면 복원하고, 없으면 사용자가 이미지를 다시 지정해야 한다.

### 검증 항목

- 글로벌·캐릭터 전용 페르소나의 고유/공유 아이콘을 만든 뒤 cleanup 및 재시작
- PNG 바이트와 `.png` 키, WebP 바이트와 `.png` 키 모두 표시
- 참조 없는 진짜 고아 자산은 계속 삭제
- 클라이언트 cleanup과 서버 자산 통계가 같은 생존 집합을 계산
- 이미 없는 자산은 placeholder로 표시하고 화면 전체 promise를 실패시키지 않음

## 6. 플러그인 업데이트 `+` 버튼 실패

### 확정된 코드 경로

- `checkPluginUpdate()`가 update URL의 앞부분을 Range 요청해 새 버전을 찾으면 `+` 버튼이 나타난다.
- 버튼은 `runInstalledPluginUpdateAction()` → `updatePlugin()` → `runPluginUpdate()`를 호출한다.
- 다운로드 HTTP 오류, fetch 예외, import의 조기 종료, 저장 실패, 설치 후 검증 실패가 모두 최종 `false`와 동일한 `pluginUpdateFailed` 토스트로 축약된다.
- 따라서 현재 사용자 메시지만으로는 어느 단계가 실패했는지 알 수 없다. 이것 자체가 확정된 진단 결함이다.
- 최근 updater는 설치 후 `previousSource !== source` 및 저장된 script와 다운로드 source의 완전 일치를 요구한다. import 함수는 여러 검증 실패에서 throw하지 않고 경고 후 `return`하므로 설치가 거부된 이유가 updater까지 전달되지 않는다.

### PageFold의 확정 실패 분기

- 기존 DB에 남은 `pagefold` 플러그인 행은 설정 목록과 update URL을 유지할 수 있다.
- UI는 이 legacy 행의 업데이트 버튼을 숨기지 않는다.
- `importPlugin()`은 내장 플러그인 이름 `pagefold`의 설치/업데이트를 명시적으로 차단한다.
- 따라서 사용자가 누른 대상이 기존 PageFold 행이면 “업데이트 감지 → `+` 표시 → 내장 플러그인 차단 → 일반 실패 토스트”가 결정적으로 발생한다.
- 다른 플러그인이라면 실제 update URL과 브라우저 콘솔/서버 로그가 있어야 다운로드, parser, 저장, strict verification 중 정확한 분기를 확정할 수 있다.

### 필요한 패치

- updater 반환값을 boolean 대신 단계와 원인을 포함한 결과로 바꾼다.

```ts
type PluginUpdateResult =
  | { ok: true; version: string }
  | { ok: false; stage: 'download' | 'parse' | 'policy' | 'save' | 'verify'; code: string; detail?: string }
```

- HTTP status, 네트워크/CORS, metadata parse, 이름 변경, API 정책, PageFold 정책, durable save, post-install verify를 구분한다.
- UI에는 안전한 현지화 메시지를 표시하고 상세 원인은 console에 남긴다. 플러그인 전체 source나 secret은 로그에 기록하지 않는다.
- update check와 실제 다운로드의 transport 정책을 통일하고, 필요하면 proxy-aware `fetchNative(GET)` 경로를 사용한다.
- legacy PageFold 행은 업데이트 버튼을 숨기고 “내장 버전 사용 중”으로 표시한다. 사용자가 원하면 별도 정리 동작으로 legacy 행만 제거하되 설정/스토리지는 보존한다.
- 일반 플러그인은 저장된 source의 문자열 완전 일치만 보지 말고 설치된 name/version/updateURL과 durable save 결과를 함께 검증한다. TypeScript 변환 등 정상적인 source 변형 가능성도 구분한다.

### 검증 항목

- PageFold legacy 행에서 update 버튼이 노출되지 않음
- 404, CORS/네트워크, 잘못된 metadata, 이름 변경, 정책 거부, 저장 실패, 검증 실패가 서로 다른 result code를 반환
- 성공은 durable save 이후에만 표시
- 사용자 argument, enabled 상태, custom storage 유지
- check 성공 후 full download 실패 및 Range 미지원 서버 처리
- Android Node 환경의 실제 update URL 한 개로 end-to-end 확인

## 7. 구현 순서

1. SQL repair status 계약과 다중 백업 후보 처리
2. Symbol 기반 SQL runtime metadata helper 및 모든 직접 접근 전환
3. 캐릭터 전용 페르소나 자산 소유권 수집과 404 fallback
4. 플러그인 update result/diagnostics 및 PageFold legacy UI 처리
5. 공통 로딩 presentation 적용
6. Android Node 환경 수동 회귀 확인

사용자 요청에 따라 구현 시 TDD 절차를 강제하지 않는다. 다만 데이터 손실과 재발 방지를 위해 위 회귀 검증은 구현 완료 후 반드시 실행한다.

## 8. 릴리스 차단 조건

- SQL 복구가 실패했는데 성공/`not-needed`로 보고되는 경우
- Svelte proxy 대상 descriptor 오류가 한 경로라도 남은 경우
- cleanup 후 캐릭터 전용 페르소나 자산이 삭제되는 경우
- 플러그인 실패가 다시 원인 없는 단일 boolean/토스트로만 끝나는 경우
- 기존 설정 gate 범위 또는 캐릭터 overlay lifecycle이 바뀌는 경우

## 9. 문서화된 미확정 사항

- 사용자 Android 데이터에 직접 접근할 수 없어 이미 깨진 각 페르소나 icon key의 KV 존재 여부와 HTTP 404는 대조하지 못했다. 코드에는 해당 파일을 삭제하는 확정 경로가 존재한다.
- 실패한 플러그인 이름과 update URL이 제공되지 않았다. PageFold라면 직접 원인이 확정되며, 그 외 플러그인은 새 단계별 진단 결과 또는 현재 console 로그가 필요하다.
- 삭제된 페르소나 이미지의 원본이 백업에도 없다면 자동 복구는 불가능하다.
