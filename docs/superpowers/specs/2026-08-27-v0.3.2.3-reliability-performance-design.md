# RisuVault v0.3.2.3 Reliability and Performance Design

## Purpose

v0.3.2.3 fixes all user-reported regressions in one release while treating startup latency as the primary product requirement. The release must stop repeated legacy-to-SQL migration, move normal startup onto a small metadata-first path, import CharX archives larger than 256 MiB over direct local/LAN connections, restore installed-plugin updates, and correct message-page navigation.

Cloudflare tunnel uploads are outside this release. Direct browser access to the Node server over localhost or LAN is the supported large-import path.

## Success criteria

- A successful legacy migration runs exactly once. Browser reload and server restart both open the existing SQL database without reading, decoding, cloning, or resubmitting `database.bin`.
- Migration failures are visible and durable. The application must not quietly continue in legacy mode and retry the same work on every reload.
- Normal startup returns only the data required to paint the character/chat shell. Plugin state, presets, modules, personas, update checks, model recovery, and other noncritical work do not delay first interaction.
- Bootstrap response construction is revision-cached and exposes timing and payload metrics. The final Android check compares first-interactive timing with the supplied Haejeok reference, whose character list appears at roughly three seconds.
- Direct local/LAN Node imports accept valid CharX archives larger than 256 MiB without loading the complete archive or a large contained asset into browser or server memory.
- Large assets contained in an accepted CharX archive are preserved rather than silently omitted because of the existing 50 MiB per-asset policy.
- The plugin-tab `+` action updates an already installed plugin through the existing in-app workflow.
- Advancing from page `1/3` to `2/3` positions the message list at the top of page 2, not the bottom of page 1.

## Chosen approach

Use a focused hybrid rather than replacing RisuVault storage wholesale with Haejeok or applying isolated limit increases. RisuVault keeps its relational SQLite and file-native asset model, but adopts Haejeok's useful startup boundaries: shallow canonical data first, early shell reveal, deferred domain hydration, and revision-aware bootstrap reuse.

This approach minimizes schema and compatibility risk while removing the two architectural causes of the observed behavior: client-side full-database migration through a bounded JSON endpoint and eager work on the first-interactive path.

## SQL migration design

### Server-owned migration

The standalone server owns the legacy source and the target SQLite database, so migration must remain on the server. When SQL reports `empty`, the client requests a dedicated authenticated migration operation. The server reads its canonical legacy `database/database.bin`, decodes it locally, converts it into relational rows, and commits one atomic replacement without sending the database graph through Express JSON.

The operation uses an explicit migration state stored alongside SQL metadata:

- `empty`: no successful migration has begun or completed;
- `migrating`: one server operation owns the migration;
- `ready`: the committed revision is canonical;
- `failed`: the previous attempt failed with a sanitized diagnostic.

Only `empty` may start migration. `migrating` rejects or joins duplicate requests, `ready` returns the existing revision, and `failed` requires an explicit retry rather than automatic reload loops. The successful transaction sets `ready` and checkpoints before the response is acknowledged.

### Client behavior

The client first requests the shallow SQL bootstrap. `ready` activates SQL immediately. `empty` calls the dedicated migration endpoint once, verifies the returned revision with a fresh bootstrap, and activates the result. `failed`, authentication failures, unsupported servers, and transport errors display distinct actionable errors.

The client never treats an ambiguous failure as `empty`. It may use an explicit recovery snapshot only for the existing degraded recovery workflow; it must not silently select legacy storage as the normal runtime after an unsuccessful migration.

## Startup performance design

### Bootstrap contract

The first SQL response contains only:

- essential display and navigation settings;
- character summaries;
- chat summaries and durable message counts;
- the active selection identifiers and storage revision.

Large or noncritical domains are excluded: plugin custom storage, installed-plugin bodies, full bot presets, personas, lorebooks, modules, scripts, prompt collections, update metadata, and message bodies.

The server caches the serialized bootstrap by SQL revision and invalidates it only when a commit changes a bootstrap-owned domain. It supports ETag/revision validation so an unchanged reload avoids reconstructing and retransmitting the response.

### First-interactive boundary

After shallow SQL data is accepted, the client applies language, theme, viewport, and essential navigation state and then sets the loaded/interactive state. It schedules domain hydration, plugin loading, model registration, update checks, session establishment, cleanup, and job recovery after the browser has painted.

Startup metrics separately record server bootstrap construction, response transfer, JSON parsing, client reconstruction, and first interaction. This makes future regressions attributable rather than hidden behind one aggregate loading message.

## Large CharX design

The direct Node route continues to receive the browser `File` as a streamed request and spool it to an owned temporary file. The 256 MiB compressed-archive hard cap is removed from the supported local/LAN path. Admission is instead controlled by available disk space, a configurable decompressed-total ceiling, entry-count limits, validated ZIP metadata, and bounded extraction queues.

The 50 MiB per-asset exclusion is removed for this streamed path. Assets are hashed and published from files, not accumulated in memory. Card and module metadata keep bounded limits because they are parsed as structured data. ZIP-bomb protection retains total decompressed size and adds an expansion-ratio check; unsafe paths, duplicate names, CRC mismatches, unsupported ZIP structures, and insufficient disk remain hard failures.

Progress distinguishes upload, validation, extraction, publication, and finalization. Errors identify archive limit, decompression safety, malformed archive, storage exhaustion, session conflict, or publication failure.

## Plugin update design

The plugin tab must distinguish adding a new plugin from updating an installed plugin. Activating `+` for an existing plugin identity resolves the latest source through the same trusted import/update path, preserves compatible plugin custom storage, replaces the installed definition atomically, reloads the plugin registry, and reports success or the concrete failure. A duplicate-install no-op is not considered success.

## Message navigation design

Page changes have an explicit destination anchor. Forward navigation computes the next page first, renders it, and then scrolls the message container to that page's top anchor. Backward navigation uses the corresponding intended anchor without reusing stale pre-render measurements. Scroll restoration is tied to the rendered page identity so delayed hydration cannot apply the previous page's bottom position.

## Error handling

- Migration responses use stable error codes and sanitized messages; server paths and raw SQL never reach the client.
- No migration or import error is converted into a successful legacy fallback.
- Large import staging data is removed on success, failure, abort, and disconnect.
- Revision conflicts and concurrent migrations/imports return explicit conflict states.
- Startup can reveal a recovery action, but it never loops automatically on a known failed state.

## Verification strategy

Testing is deliberately scenario-focused rather than split into many microscopic cases.

1. One SQL lifecycle integration scenario creates a legacy database, migrates it, reloads the client contract, closes and reopens SQLite, and proves the second and third boots do not access or migrate the legacy source.
2. One startup contract scenario verifies the bootstrap excludes deferred domains, is stable across message-count growth, is reused for an unchanged revision, and records bounded construction/payload metrics.
3. One CharX integration scenario streams a generated archive above 256 MiB containing an asset above 50 MiB, verifies byte-identical publication, and verifies cleanup. The heavy-size form may run under the existing opt-in large-import harness, while regular tests exercise the same streaming path with scaled fixtures.
4. One plugin regression scenario proves the `+` action replaces an installed version and preserves custom storage.
5. One message-navigation scenario renders adjacent pages and proves forward navigation lands on the next page's top anchor.
6. Release verification runs the affected client/server suites, type checking, production build, and a direct local/LAN manual smoke test. Android timing is measured over multiple warm-server runs and compared with the supplied reference video.

## Parallel implementation boundaries

- SQL/startup worker: migration state and endpoint, shallow bootstrap cache, client boot selection, lifecycle/performance scenarios.
- CharX worker: admission policy, streamed large assets, decompression safeguards, large-import scenario.
- UI worker: plugin update action and message-page anchor behavior with focused regressions.
- Main integrator: shared contracts, conflict resolution, full verification, performance review, release notes, and version metadata.

Workers must not modify another worker's owned subsystem without coordinating through the main integrator. Production behavior changes use focused test-first cycles; documentation, generated fixtures, and wiring-only changes do not require redundant micro-tests.

## Release boundaries

The release does not add Cloudflare-compatible resumable uploads, change the CharX file format, replace relational SQLite, introduce a new UI design, or perform unrelated refactors. Existing data remains recoverable through the pre-migration backup and explicit recovery path.
