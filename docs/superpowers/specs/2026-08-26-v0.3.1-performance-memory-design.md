# RisuVault v0.3.1 Performance and Memory Design

Status: written specification approved by the user on 2026-08-26.

## Objective

RisuVault v0.3.1 will reduce cold-start latency, interaction jank, and mobile renderer memory growth without changing the external `.charx`, `.risum`, or backup formats. The release targets the Node deployment used remotely through Tailscale.

The central rule is that browser work and browser memory must be bounded by the active view or current operation, not by the total database, asset library, or import-file size.

## Supported Performance Profile

- Client: iPhone 13 or newer, iOS 17 or newer, Safari or installed PWA.
- Network: remote Node server accessed through Tailscale on an ordinary mobile connection.
- Reference data: 200 characters, 20,000 messages, and 20 GiB of server-side assets.
- Large import: one `.risum` file up to 3 GiB; the default upload allowance is 4 GiB.
- Cold-start goal: the character list is interactive within 5 seconds under ordinary conditions.
- Cold-start release ceiling: p95 at or below 8 seconds across the defined test run.

These are release-gate targets rather than universal guarantees. WebKit does not expose a reliable total-process memory API, and its process also includes decoded images and GPU resources. RisuVault will therefore enforce deterministic resource budgets and validate survival and responsiveness on real devices.

## Non-goals

- No full rewrite of the existing relational SQLite database.
- No change to published interchange or backup formats.
- No browser-side support for multi-GiB `.risum` parsing in Node mode.
- No attempt to guarantee an exact WebKit process-memory number on every iOS build.
- No plugin-system redesign in v0.3.1.

## 1. Metadata-first startup

Normal Node startup must not call the current full `/api/sql/snapshot` route. That route remains available for recovery and compatibility only.

The server will provide bounded query endpoints:

- `GET /api/sql/bootstrap` returns the current revision, the settings needed for first paint, selected character/chat identifiers, character summaries, and chat summaries needed for the initial selection.
- `GET /api/sql/characters/:id` returns one character's details and chat summaries, but no message bodies.
- `GET /api/sql/chats/:id/messages?before=<position>&limit=<n>` returns a reverse page of messages. The client default is 40 and the server maximum is 100.
- Targeted entity reads are available for revision-conflict recovery, so a conflict does not force a full snapshot reload.

The client will keep summary data separate from hydrated runtime data. Character and chat stubs preserve identity, ordering, and existing navigation behavior. Only the selected character details and selected message page are hydrated. Core UI paths will use the bounded repository API instead of assuming the complete object graph is resident.

The application becomes interactive as soon as bootstrap metadata and the initial character summaries are ready. Plugin loading, update checks, data cleanup, and large editor modules move after first paint. Features that require a plugin remain temporarily disabled until that plugin is ready.

## 2. Bounded runtime cache and automatic saver mode

The client will enforce resource-count and byte-count budgets because Safari cannot reliably report total process memory.

Normal limits:

- At most two chats have hydrated message data.
- The chat DOM contains at most 60 messages around the current position.
- Earlier messages are replaced by measured spacers so scroll position remains stable.
- The mobile/Simple character list (Grid Catalog `selected === 3`) uses viewport virtualization. Desktop Grid, List, and Trash modes remain follow-up work.
- Lists request server-generated WebP thumbnails; full-resolution images load only in detail views.
- Markdown, editor, preview, and image caches use bounded LRU policies.

Automatic saver mode activates during a large import/export, after resource budgets are reached, after repeated long tasks, or when the page remains in the background. It performs the following ordered actions:

1. Flush dirty user data.
2. Evict all hydrated chats except the active chat.
3. Reduce the active DOM window from 60 to 40 messages.
4. Clear full-resolution images and shrink thumbnail, Markdown, preview, and editor caches.
5. Coalesce streaming rendering to animation frames and temporarily reduce nonessential animations or live previews.

The active message, composer draft, and unsaved user changes are never evicted. Evicted content is reloadable from SQLite.

The engineering soft budget is 800 MiB of app-controlled resources, with increasingly aggressive cleanup around the equivalent of 1.0 GiB and refusal of browser-local heavy operations around 1.2 GiB. Since Safari cannot expose those totals, concrete cache and decoded-pixel limits are the enforcement mechanism; real-device profiling validates the resulting process behavior.

## 3. Row-scoped persistence

The current hot path performs deep observation, full-database structured clones, and full-graph delta comparisons. v0.3.1 introduces a Dirty Registry with these scopes:

- root setting keys;
- character IDs;
- chat IDs and ordering manifests;
- message IDs and ordering manifests;
- presets and plugin storage keys.

Core mutations register their affected IDs. Writes are coalesced for 300–500 ms and committed through the existing revisioned SQL commit mechanism. Streaming generation updates UI state immediately, persists at a bounded interval, and always commits on generation completion.

Revision conflicts reload and merge only the affected entities. Existing session/writer-lock protections remain in force.

Legacy plugin mutations that bypass the new mutation API retain a compatibility audit. That audit runs at idle priority or in a worker and is not part of token rendering, typing, scrolling, or the ordinary save path. It is a fallback rather than the primary persistence mechanism.

No full user-data migration is required because relational schema v3 already separates characters, chats, and messages and already has the indexes needed for the specified bounded queries. The 0.3.1 baseline therefore keeps schema v3 unchanged. If implementation profiling contradicts this assumption, the design must be revised and reviewed before any additive migration is introduced; it is not an implicit part of this release.

## 4. Rendering and image delivery

- Message rendering is windowed to 30–60 mounted messages.
- Streaming Markdown work is coalesced to animation frames and limited to the active message.
- Unchanged message parse results are memoized without concatenating or `JSON.stringify`-ing the entire message value on every update.
- The mobile/Simple character list is virtualized; other character grid/detail/trash modes are out of Task 7 scope.
- A server thumbnail route produces bounded-dimension WebP images and revalidates stable URLs against ETags keyed by the source object identity.
- `<img>` elements use lazy loading and asynchronous decoding where applicable.
- Full-resolution image references and temporary object URLs are released when their detail view closes.
- Settings pages, large editors, and other non-startup components are dynamically imported.

## 5. Server-assisted `.risum` import

The external `.risum` format remains unchanged. In Node mode, the browser sends the original `File` to a raw authenticated import endpoint without calling `arrayBuffer()` or constructing a base64 payload.

The endpoint uses NDJSON events and reports these phases: upload, validation, asset processing, publish, and module registration.

Server flow:

1. Authenticate, verify the active session, acquire the import lock, rate-limit, and check initial disk headroom.
2. Stream the request into an owned staging file while enforcing the compressed-upload limit and reacting to disconnect/abort.
3. Validate magic, version, declared lengths, entry count, and bounds before trusting offsets or allocating output.
4. Parse module metadata and assets sequentially. Decompression runs in a worker or cooperatively yielding task and writes output to staging files in bounded chunks.
5. Hash and stage each asset immediately; do not retain all compressed or decoded assets in memory.
6. Atomically publish the content-addressed asset keys and return the rewritten module metadata only after every entry succeeds.
7. Register the module on the client after the server returns success. Any failure cleans the owned staging directory and leaves no partial module.

Default operational limits:

- compressed upload: 4 GiB;
- module metadata: 64 MiB;
- entry count: 100,000;
- one decoded asset: 256 MiB, streamed to disk rather than retained as one browser buffer;
- total decoded bytes: 32 GiB by default, configurable by the server operator;
- disk reserve: the import is rejected before or during processing when staged bytes plus the configured safety reserve exceed available space.

Limits are configurable but never disabled implicitly. Length arithmetic is overflow-safe. Asset names are not interpreted as filesystem paths. Publication is content-addressed and atomic. Stable error codes distinguish invalid format, configured limits, insufficient storage, abort, and publish failure.

Non-Node environments retain the existing local importer. Mobile local imports above a conservative threshold are rejected with guidance to use the Node server instead of risking a renderer OOM.

## 6. Other large-data paths

The existing base64 JSON bulk-asset upload becomes a compatibility fallback. New Node paths use binary or multipart streaming with bounded concurrency.

The save-folder ZIP upload, which currently buffers the request and archive, moves to disk spooling and streaming extraction. It enforces path safety, entry limits, decoded-size limits, expansion-ratio checks, disk headroom, abort cleanup, and atomic publication. Backup import/export keeps its existing streaming transport and is covered by the same memory regression tests.

## 7. Failure handling and fallback

- Before the first v0.3.1 storage activation, the server creates a recoverable backup.
- The approved baseline performs no schema change; any later approved additive change must be transactional.
- Unsupported server capabilities produce an update prompt rather than silently falling back to an unsafe multi-GiB browser operation.
- Startup endpoint failure can use the recovery snapshot path with an explicit degraded-mode message.
- Saver-mode eviction always follows a successful dirty-data flush or retains the dirty entity in memory.
- Imports clean up on upload abort, response disconnect, disk exhaustion, malformed lengths, decoder failure, process restart recovery, and publication failure.
- Errors shown to the user name the failed phase and whether retrying is safe.

## 8. Measurement and release gates

Instrumentation uses `performance.mark`/`performance.measure` for bootstrap fetch, JSON parse, first interactive list, character hydration, message-page fetch, commit latency, and render batches. Long Tasks are sampled where the browser exposes the API. No user content is logged.

Release gates for the reference profile:

- interactive character list target: 5 seconds;
- cold-start p95 ceiling: 8 seconds;
- recent messages visible after chat selection: p95 at or below 1.5 seconds;
- steady-state long tasks over 100 ms: no more than two per minute in the scripted interaction run;
- streaming and scrolling frame delay: p95 at or below 50 ms;
- 30-minute iPhone interaction run: no WebKit termination, forced reload, or lost draft;
- 3 GiB `.risum` import: browser memory does not grow with file size and the tab remains interactive;
- server `.risum` import RSS increase target: at or below 512 MiB over baseline;
- cancellation, disk-full, corrupt input, and restart tests leave no partial module or orphaned published asset.

The automated suite uses generated fixtures rather than checked-in giant files. It includes unit tests, client/server contract tests, streaming integration tests, deterministic failure injection, and bounded-memory regression harnesses. Final release approval also requires an iPhone 13+/iOS 17+ Safari or PWA run through Tailscale and an Android Chrome regression run.

## 9. Delivery boundaries

The work will be implemented in ordered, reviewable slices: measurement first, metadata startup, bounded hydration/cache, row-scoped persistence, rendering/thumbnails, server `.risum`, remaining large-data transports, and final device validation. Each slice keeps a compatibility fallback until its replacement is verified.

Implementation and review will be performed primarily by `gpt-5.6-terra` subagents at `medium` reasoning, as requested. Only one implementation agent edits a shared slice at a time; independent read-only investigations and reviews may run in parallel.
